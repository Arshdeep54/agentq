title: Introduction
---

agentq is an embeddable job queue for agent tool calls. It runs inside your own
process. There is no Redis, no separate service, and nothing to deploy.

It exists to solve one specific problem: **a retried unit of work should not be
executed twice.**

## The problem

Agent frameworks retry failed tool calls. If a call actually succeeded but the
acknowledgment was lost, a naive retry runs it again. You get duplicate writes,
duplicate charges, and corrupted state.

The second problem arrives right behind it. When a batch of calls fails at once,
the retries all fire at once too, against whatever rate-limited or metered API
you were talking to.

Durable execution platforms solve both, but they want you to run a separate
service and adopt their workflow model. agentq is the small version: the
primitives that stop the bleeding, embedded directly in your binary.

## What you get

<CardGroup cols={2}>
  <Card title="Idempotency with cached results">
    Push a key that already completed and you get its output back from cache.
    Push one that is still running and you join it.
  </Card>
  <Card title="Per-lane concurrency">
    Each priority lane has its own capacity and concurrency limit, so cheap and
    expensive work get separate budgets.
  </Card>
  <Card title="Backpressure">
    Lanes are bounded. When one fills, pushing waits rather than growing without
    limit.
  </Card>
  <Card title="Failure isolation">
    A job that errors, or panics outright, records a terminal state and leaves
    every other job untouched.
  </Card>
  <Card title="Durable workflows">
    Ordered multi-step execution with per-step retry, built on top of the same
    queue, with status and event history persisted by a pluggable store.
  </Card>
</CardGroup>

## When not to use it

The raw `Queue` deliberately does not persist anything on its own. Everything
lives in your binary; if it dies, queued work dies with it. If a step's state
needs to survive a restart, reach for a [durable
workflow](/guides/workflows) instead of the raw queue.

Either way, agentq does not coordinate across processes. If you need a queue
shared across machines, you want a broker-backed queue instead.
